## Context

`extractWithModel` (`prototypes/studio/api/_model.ts`) has two branches selected by `resolved.profile`:

- **`general`** (Anthropic, OpenAI, Google, Codex CLI, Claude Code, OpenAI-compatible, and Ollama when not using NuExtract raw): calls `generateWithGenericJsonPrompt`, which builds a `generateText` request whose only shape constraint is the text instruction `EXTRACTION_SCOPE_GUARDRAIL` ("Only extract fields defined in the Extraction Schema above..."). `Output.json()` is applied only when the provider's static `jsonOutput` capability is `'native'` (`prototypes/studio/api/_provider.ts`) — and that only guarantees syntactically valid JSON, not a constrained key set. **Anthropic is registered with `jsonOutput: 'prompt'`**, so today Claude gets *no* structural constraint at all, text instruction only.
- **`nuextract-raw`**: unaffected by this change, out of scope. Confirmed deliberately, not just by default: NuExtract's resistance to schema-external keys is a training-time property (it's fine-tuned specifically to fill a given template's key structure), a different and already-strong mechanism unrelated to the bug this change fixes (which is specific to general chat models improvising past a text-only instruction). Bolting Ollama's own `format` grammar constraint onto the NuExtract raw path was considered and rejected: that path bypasses the AI SDK's `generateText`/`doGenerate` entirely via a hand-built `fetch('api/generate', { raw: true, ... })` call with NuExtract's own control-token protocol (`<think>...</think>`, `【template_start】`, etc. — see `renderNuExtractPrompt`), so a grammar constraint forcing the whole raw completion into schema-shaped JSON from token one is untested against that prefix content and risks the same class of silent-incompatibility already documented for this exact endpoint (`chat_template_kwargs` being ignored, per `prototypes/studio/CLAUDE.md`).

All three CATALOG/Article call sites in `packages/extraction/src/module.ts` (`executeArticle`, the `document-values` stage, and the per-record CATALOG loop) funnel through one `invoke()` helper that calls the injected `ExtractionModel.extract(...)`, which Studio wires directly to `extractWithModel` (`prototypes/studio/api/_extraction_runtime.ts`). So a single fix inside `extractWithModel`'s general branch covers every strategy.

**Addendum (found during implementation):** `extractWithModel` is not only the `ExtractionModel.extract` implementation — `_extraction_runtime.ts`'s `groundingModelFor(target).ground(...)` (the `GroundingModel` backing `groundExtraction` in `packages/extraction/src/grounding.ts`) also calls `extractWithModel` directly, with a synthetic `template: { links: { <claimLabel>: 'verbatim-string', ... } } }`. Both `modelFor` and `groundingModelFor` share the same `target`, so this change's schema derivation applies to grounding calls too, not just extraction calls, whenever `resolved.profile === 'general'`. This was not called out in the original proposal (which framed the bug purely in terms of the Extraction Result), but is harmless and arguably beneficial by the same reasoning: grounding's own `groundingSelections` validation in `_extraction_runtime.ts` already requires an exact `{links: {...}}` shape, so constraining generation to that same shape up front is consistent, not a new restriction — a schema derived from `{name: 'verbatim-string'}`-style claim templates just produces `z.object({<claimLabel>: z.string().nullable().optional(), ...}).strict()` nested under `links`, which tolerates a claim being left unanswered (already a valid, separately-handled `missing_claim` outcome) and only closes off keys the grounding contract never allowed anyway. Covered by a dedicated test in `_model.test.ts` rather than by scoping it out.

The `template: unknown` object `extractWithModel` receives is always `stripDescriptions({ _description, ...nodesToTemplate(nodes) })` (with `_description` stripped) — i.e. a plain object/array literal shaped exactly like the expected result, using type-token scalar values (see `packages/extraction/src/schema.ts`). Critically, `packages/extraction/src/schema.ts` already exports `templateToNodes(value: unknown): SchemaNode[]`, the exact inverse of `nodesToTemplate`, used today by the schema-editor round trip. This means the general branch can reconstruct the `SchemaNode[]` shape from the `template` it already receives — no new data needs to be threaded through the `ExtractionModel` interface boundary.

The `ai` SDK (v7, already a dependency) exposes `Output.object({ schema })` (`FlexibleSchema`, e.g. a Zod schema) distinct from `Output.json()`. Unlike `Output.json()`, `Output.object()` is provider-agnostic: the SDK uses the provider's native structured-output mode when available and falls back to tool-calling otherwise, so it does not require gating on the `jsonOutput` capability flag. `generateWithGenericJsonPrompt` already has a `NoObjectGeneratedError` catch that degrades to the model's raw `error.text` when structured generation fails to parse (currently scoped to `target.jsonOutput === 'native'`); the same fallback pattern covers a provider/model that can't honor `Output.object()` for some reason, so adopting it is not a new failure mode — worst case reproduces today's plain-text behavior.

Both CLI-backed general-profile providers (`codex-cli`, `claude-code` — `execution: ['general']` only, so any target they resolve to is always `profile: 'general'`) independently honor `responseFormat.schema` in their AI SDK adapters, confirmed by reading each package: `ai-sdk-provider-claude-code` routes it through the Claude Code CLI's own internal structured-output tool call; `ai-sdk-provider-codex-cli` writes the schema to a temp file and passes `--output-schema <path>` to the Codex CLI process (`dist/index.js:1465-1478`). Neither needs provider-specific code in `_model.ts` — both fall out of the same general-branch change as Anthropic/OpenAI/Google/openai-compatible/general-profile Ollama.

## Goals / Non-Goals

**Goals:**
- When the general branch of `extractWithModel` can derive a schema from the `template` it receives, request generation constrained to that schema's exact key set instead of relying solely on `EXTRACTION_SCOPE_GUARDRAIL`.
- Preserve today's error surface: a model that still cannot honor the constraint degrades the same way unconstrained generation does today (raw text goes through the existing `parseExtractionResult` → `restoreSchemaNodeOrder` validation, which still rejects genuinely unknown keys as a defence-in-depth backstop).
- Do not require any new per-provider capability metadata; reuse `templateToNodes` rather than threading `SchemaNode[]` through the `ExtractionModel` interface.

**Non-Goals:**
- Changing the `nuextract-raw` path, `generateSchemaWithModel` (schema suggestion), or `generateSchemaEditJson`.
- Making every field mandatory. A field the model can't find in the source must remain omissible/nullable — the goal is closing the *unknown-key* hole, not forcing fabrication of missing values (which would trade one failure mode for a worse one).
- Introducing a new `jsonOutput`-style capability flag; `Output.object()`'s fallback behavior is handled by the AI SDK itself.

## Decisions

**Derive a Zod schema from `SchemaNode[]`, reconstructed via `templateToNodes(template)`, inside `packages/extraction/src/schema.ts`.**
Add an exported `schemaNodesToZod(nodes: SchemaNode[]): z.ZodType` (name TBD at implementation time) that maps:
- `'string' | 'verbatim-string' | 'date'` → `z.string()`
- `'number'` → `z.number()`, `'integer'` → `z.number().int()`, `'boolean'` → `z.boolean()`
- a node with `allowedValues` → `z.enum(allowedValues)`
- `type: 'array'` with `itemType` → `z.array(<scalar mapping>)`
- `type: 'object' | 'array'` with `children` → nested `z.object({...}).strict()` (wrapped in `z.array(...)` for `'array'`)
- every object level uses `.strict()` — this is the actual key-set enforcement; Zod's `.strict()` rejects unrecognized keys during `generateText`'s internal object validation, so a model that adds `description` fails *validation immediately with a clear error*, or (with `Output.object`) the SDK's tool-calling constraint prevents the extra key from being generated in the first place for providers that honor tool-input schemas strictly.
- every field is `.nullable().optional()` unless the schema doesn't already treat absence specially — match today's tolerance for omitted/`null` values so this change is additive (rejects extra keys) without becoming stricter about missing ones.

Reuse `templateToNodes(extractionTemplate)` in `_model.ts` rather than changing `ExtractModelInput`/`ExtractionModel.extract` to also carry `SchemaNode[]`. This keeps the change local to `_model.ts` + `schema.ts` and avoids touching the `ExtractionModel` interface, `module.ts` call sites, or the NuExtract path.

**Use `Output.object({ schema })` unconditionally in the general branch when derivation succeeds; keep today's behavior as the fallback.**
Wrap the `templateToNodes` + `schemaNodesToZod` call in a `try/catch` inside `generateWithGenericJsonPrompt`'s caller (`extractWithModel`): if derivation throws (an unexpected/legacy template shape), fall back to today's `Output.json()`-or-nothing behavior unchanged, so this change can never make a previously-working extraction fail to *start*. Drop the `target.jsonOutput === 'native'` gate for this new path — `Output.object()` supersedes `Output.json()` when a schema is available.

**Correction found during implementation:** `try/catch` alone is not sufficient. `templateToNodes` degrades a non-record input to `[]` rather than throwing (`if (!isRecord(value)) return []`), which `schemaNodesToZod([])` happily turns into a *valid* `z.object({}).strict()` — a schema that rejects every field, not one that fails derivation. A template that is not a plain record (e.g. an array, from a caller `extractWithModel` doesn't currently have but shouldn't be trusted to never gain) would silently over-constrain instead of falling back. Fixed by adding a `deriveExtractionSchema(template)` helper in `_model.ts` that checks `isRecord(template)` before attempting derivation at all, returning `undefined` otherwise — the `try/catch` remains for any other unexpected throw, but the `isRecord` guard is what actually protects the "unconvertible shape" case.

**Keep `EXTRACTION_SCOPE_GUARDRAIL` and `restoreSchemaNodeOrder`'s strict rejection as-is.**
They remain the backstop for: (a) the NuExtract raw path (unchanged), (b) the fallback branch above, and (c) any provider whose `Output.object()` support still lets an extra key slip through despite the schema (defence-in-depth, cheap to keep).

**No Ollama-specific code needed for this to also cover general-profile Ollama routes.** `ollama`'s provider entry has `execution: ['general', 'nuextract-raw']` — when an execution target resolves to Ollama through the `general` profile (not the NuExtract raw path above), it's driven by the `ai-sdk-ollama` package, which already maps `Output.object()`'s `responseFormat.schema` straight onto Ollama's own native `format` request field (a real GBNF-grammar-constrained decode, done server-side by Ollama/llama.cpp — confirmed in `ai-sdk-ollama`'s `dist/index.browser.js`). So general-profile Ollama gets a hard schema guarantee for free the moment `extractWithModel`'s general branch passes a schema, with no Ollama-aware branching in `_model.ts`.

## Risks / Trade-offs

- **[Risk] A provider/model in the `general` profile has weak or no tool-calling support, and `Output.object()` behaves worse than plain-text `generateText` for it (e.g. higher latency, extra round-trips, or outright unsupported).** → Mitigation: the existing `NoObjectGeneratedError` catch already degrades to raw text; extend its condition to also cover the schema-based path so a hard failure there reproduces exactly today's behavior rather than a new failure mode. Confirm via `_model.live.test.ts`-style live checks against at least Anthropic (the provider that motivated this change) before relying on it broadly.
- **[Risk] `templateToNodes` is a lossy inverse for template shapes `nodesToTemplate` never produces itself (e.g. hand-constructed templates in tests or future callers).** → Mitigation: derivation is wrapped in try/catch with a fallback to current behavior (see Decisions), so an unrecognized shape degrades gracefully instead of breaking extraction.
- **[Trade-off] Building a second `SchemaNode[]` → Zod conversion (distinct from the existing `SchemaNode[]` → template conversion) adds a bit of duplicate structural knowledge in `schema.ts`.** → Accepted: both conversions are small, colocated, and covered by the same test file; the alternative (deriving a JSON Schema textually instead of via Zod) would still need the same type-mapping logic and lose Zod's `.strict()` validation for free.
