## Why

Whole-document, single-pass extraction (today's only path in `extractWithModel`) asks the model to read an entire multi-record source document — e.g. an archaeological field report describing 7 graves — and return every record in one response. This collapses record-level context: when similar phrasing or values repeat across records, the model (and, downstream, the PDF evidence search) has no reliable way to tell which occurrence belongs to which record. The historical FREE-technical prototype addressed this for "Catalog"-shaped documents (many structurally similar records, e.g. one section per grave) with a boundary-detect → slice → per-record-extract → merge pipeline, kept separate from an "Article" strategy (a single continuous document, e.g. a journal article) that always ran one whole-document pass. That two-strategy split does not exist in the current codebase, and the extraction pipeline itself was never ported — only a same-named, semantically different Streamlit reference exists.

A heading-based lightweight version of the Catalog side of this has already been implemented directly in `_model.ts`/`_catalog_sections.ts` (no LLM boundary-detection call — record boundaries are inferred from the recurring level-1 Markdown heading pattern the parsing service already emits, and each section's model call runs concurrently). It currently activates automatically whenever a schema has exactly one repeated-array field and the document's headings show a recurring pattern. That auto-heuristic has a real failure mode: an Article-type document (e.g. a journal article using generic numbered section headings like "Section 1"/"Section 2") can accidentally match the recurring-heading-shape check and get incorrectly sectioned as if it were a Catalog, fragmenting what should be one holistic extraction. Restoring an explicit Catalog/Article classification — decided by the researcher, not inferred — closes that gap.

## What Changes

- **(Implemented)** `_catalog_sections.ts`: pure helpers that detect a schema's sole repeated-array field (`findPrimaryArrayKey`), split canonical Markdown into record-aligned sections by recurring level-1 heading shape rather than every heading (`splitMarkdownByHeadings`, `sectionContainsTable`), and compute/remap each section's absolute page from the parsing service's `\n\n---\n\n` page-break sentinel (`pageForOffset`, `offsetPageNumbers`).
- **(Implemented)** `_model.ts`: `extractWithModel` takes the sectioned path when a document has parsed Markdown, the schema qualifies, and the heading pattern recurs — running one concurrent, capped extraction call per section (reusing the existing `runWithConcurrencyLimit` helper) instead of one whole-document call — falling back unchanged to the single whole-document pass otherwise.
- **(Implemented)** Restored an explicit Catalog/Article strategy, chosen by the researcher, gating the sectioned path: sectioning is only attempted when the strategy is `'catalog'`; an `'article'`-marked (or unmarked/legacy) schema always takes the single whole-document pass regardless of heading structure. **Not** bound to the schema template itself as originally planned (see design.md Decision 5's mid-implementation correction) — bound to the schema's lifetime as `App.tsx` state instead, since this codebase's `useExtraction.ts` already wraps the researcher's schema as `{ records: [template] }` before sending, and `SchemaNode[]` has no root-metadata slot to carry a whole-schema flag through.
- **(Implemented)** Moved the choice earlier: the researcher picks Catalog/Article *before* generating a schema, not only before running extraction, and the choice now shapes the schema-generation prompt itself (`schemaPrompt`) — a Catalog schema is guided to describe one occurrence's shape directly, since sectioned extraction already supplies the repetition, instead of the pre-existing (Article-oriented) guidance to model repetition as an array field.

## Capabilities

### New Capabilities
- `catalog-section-extraction`: heading-based document sectioning and concurrent per-section extraction for schemas whose primary target is one repeated array of records, as an alternative to a single whole-document extraction call — including the explicit Catalog/Article strategy that gates it.

### Modified Capabilities
None — the strategy classification turned out not to touch `schema-node-persistence` (see design.md Decision 5); it lives entirely within the new `catalog-section-extraction` capability instead.

## Impact

- Backend: `prototypes/studio/api/_catalog_sections.ts` (new), `_model.ts` (extraction gating + `generateSchemaWithModel` threads `strategy` to `schemaPrompt`), `_evidence_template.ts` (excludes `_strategy` the same way it already excluded `_description`), `_schema.ts` (`schemaPrompt` gains strategy-aware guidance), `generate_schema.ts` (parses `strategy` from the request form). No `extract.ts` change — extraction reads strategy from the template, not a new request field.
- Frontend: `useExtraction.ts` (sends `_strategy` alongside its existing `{ records: [template] }` wrapper), `App.tsx` (owns `extractionStrategy` state — reset only on a new PDF, survives schema generation, passed into both `requestSchema` and `useExtraction`), `RightRail.tsx` (threads the prop through), `SchemaPanel.tsx` (renders a `SegmentedControl` in its header, visible in every schema state, not just once a schema exists), `api.ts` (`ExtractionStrategy` type, `requestSchema`'s `strategy` option).
- Tests: `_catalog_sections.test.ts`, `_model.test.ts` (including strategy-gating cases), `_evidence_template.test.ts` (`_strategy` drop/passthrough), `_schema.test.ts` (new — catalog vs. article vs. unset generation guidance), `extract.catalog.ellekilde.smoke.test.ts`. No hook-level test for `useExtraction.ts` (no hook-testing infra in this codebase yet) — covered by TypeScript's signature checking plus the backend gating tests.
