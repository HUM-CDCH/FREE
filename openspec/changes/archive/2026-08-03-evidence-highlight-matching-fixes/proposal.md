## Why

Evidence highlighting has two concrete failure modes reported by researchers: (1) some Extraction Result values never get highlighted at all, and (2) table row/column header hints never actually disambiguate anything in practice. Both trace back to the same root cause: `EvidenceHighlightLayer.tsx` locates evidence by re-searching the PDF's own text layer (via pdf.js `getTextContent()`) for a literal string match against `value`/`snippet` — a second, independent text extraction that doesn't reliably agree, character-for-character, with the canonical Markdown the parsing service already produced and the model actually read (different extraction pipeline, different normalization, no tolerance for the model normalizing a typed field's value away from its literal source wording).

Investigating a fix surfaced that this project's own data model already anticipated a fundamentally better answer: `ParsedDocument.evidence_index: EvidenceIndex` exists today with the literal code comment *"no anchor producer exists yet"* (`parsed_document.py`). Investigating further found that the hard part of building one is already done by Docling: every rendered Markdown block is preceded by inline `<loc_x0><loc_y0><loc_x1><loc_y1>` location tokens carrying that block's exact bounding box (`docling_core`'s serializer, confirmed by reading its source), normalized to a 0–500 scale relative to page size — and `doctags_to_markdown.py` currently discards these tokens outright (`strip_doctag_locations`) when rendering the canonical Markdown Studio fetches.

This proposal replaces the original "add matching tolerance" scope with implementing that anchor producer: preserve the location tokens Docling already computes, map them to canonical-Markdown character offsets, and let the frontend look up a value's bounding box directly — by searching for its (verbatim) snippet in the *same* Markdown string the anchors were built from — instead of re-extracting and re-matching PDF text at render time. This closes the root cause for prose/text evidence the same way `ParsedTable.cells[].bbox` already closed it for tables.

## What Changes

- **Backend (`parsing_service`)**: `doctags_to_markdown.py` stops discarding `<loc_...>` location tokens. It sentinelizes each one during conversion (following the module's existing `_PAGE_SENTINEL`/`_TABLE_RESTART` pattern so the tokens survive every existing regex-substitution pass unchanged), then resolves them in a final pass over the fully-rendered Markdown into `{markdown_start, markdown_end, page, bbox}` anchor records — converting each block's normalized 0–500 location tokens to PDF-point coordinates using per-page width/height, which are already computed earlier in `orchestrator.py` (`PdfInspection.pages`) but not yet threaded into the Markdown conversion step.
- **Backend**: `orchestrator.py` threads page dimensions into the Markdown conversion call (following the existing `page_heights_pt`-style dict pattern already used for table extraction) and populates `ParsedDocument.evidence_index.anchors` with the resolved anchor records instead of leaving it permanently empty.
- **Frontend**: a new `markdownAnchorMatch.ts` module locates a field's bounding box by finding its verbatim `snippet` in the canonical Markdown (fetched once, already in hand as `documentMarkdown`) and looking up the anchor(s) covering that character range — no PDF re-extraction, no text-matching tolerance concerns, since both sides of the comparison are now the same Markdown string.
- **Frontend**: `EvidenceHighlightLayer.tsx` tries anchor-based lookup for text evidence (new tier, after the existing table-cell-coordinate lookup for table evidence, before the old PDF text search), falling back to the existing PDF text search unchanged when no anchors are available (the bundled demo document has no live parsing task and thus no anchors; any previously-parsed task predating this change also has none).
- **Frontend (fallback hardening, retained from the original scope)**: the PDF text search that remains as the final fallback tier gains the two smaller fixes from this change's original scope — dash-variant tolerance in text comparisons, and a snippet-location fallback when an exact value can't be pinpointed — plus `tableCellMatch.ts`'s candidate matching gains a length-gated tolerant substring fallback (borrowed from this project's own prior, never-merged table-matching attempt, which used a simpler and more defensible `min(a,b).length >= 4` substring-containment guard than a hand-rolled word-boundary regex).

## Capabilities

### New Capabilities
- `evidence-anchor-index`: parsing-service capability that preserves Docling's per-block location tokens through Markdown conversion and exposes them as `{markdown_start, markdown_end, page, bbox}` anchor records via `ParsedDocument.evidence_index.anchors`.

### Modified Capabilities
- `evidence-highlight-layer`: gains an anchor-based lookup tier (via the canonical Markdown, ahead of the PDF text-search fallback) for text evidence, plus matching-tolerance hardening (dash-variant tolerance, snippet-location fallback, tolerant table-cell substring matching) in the fallback path that still runs when anchors aren't available. (Note: this spec has pre-existing drift from a prior change — e.g. it still describes a `focusValue`/double-draw design the component no longer uses — and does not yet reflect the table-cell-coordinate-matching capability from the completed-but-unarchived `table-evidence-coordinates` change. This delta is written against the current actual code, not the stale spec text, and does not attempt to reconcile that pre-existing drift.)

## Impact

- Backend: `prototypes/parsing_service/app/parsing/doctags_to_markdown.py` (location-token sentinelizing + final anchor-resolution pass, new return field), `orchestrator.py` (thread page dimensions into the conversion call, populate `evidence_index.anchors`), `app/models/parsed_document.py` (tighten `EvidenceIndex.anchors`'s type from `list[dict[str, Any]]` to a proper model), `docling_runner.py` (`_convert_doctags`/`run_docling_ingestion` signatures gain a page-dimensions parameter).
- Frontend: new `prototypes/studio/src/markdownAnchorMatch.ts`, `parsedDocument.ts` (new `EvidenceAnchor` type + parser), `api.ts` (fetch anchors alongside tables), `App.tsx` (thread anchors through), `EvidenceHighlightLayer.tsx` (new lookup tier, plus fallback-path tolerance fixes), `tableCellMatch.ts` (tolerant substring fallback).
- Tests: `test_doctags_to_markdown.py` (new location-token cases — the existing 26 hand-written cases contain no `<loc_...>` tokens today and are unaffected), `test_canonical_ingestion.py`/`test_docling_integration.py` (anchor population through the real pipeline), `EvidenceHighlightLayer.test.ts`/new `markdownAnchorMatch.test.ts`, `tableCellMatch.test.ts`.
- No breaking API changes — `evidence_index.anchors` is an existing, currently-always-empty field; populating it is additive.
