# PR #275 Article resolution P2 fixes: paired live-model measurement

Declared before any counted model call. Nothing below changes after the first counted call; any deviation is
reported as a deviation.

## Question

PR #275 (code `1181e93e`, resolver blob `e7037b17411bcab3ce66d2061b89e680a6e469b9`) changes two rules of the
resolver accepted on PR #267 (`dev` `811bb9f2`, blob `5a284de09aaab69fcc72847ef0fc9c6fac715942`, rerun 2):

- P2-1: a REPEAT also leaves beside an equal item labelled OTHER (before: only beside OWN).
- P2-2: a list part holds at most 60 items and no more than fit one request (before: 60, and a part that did not fit
  left the whole list unresolved with `resolution_exceeds_budget`).

What does each change delete and retain, compared with the accepted resolver on the same readings, (a) on the 12
annotated papers that accepted it and (b) on long-list documents where the two P2s occur?

## Inputs

- Corpus: the 12 annotated collagen papers, sealed gold, B1 schema as amended by
  `../pr267-resolution-comparison/amendment-1.md` (`harness/schema-collagen.json`, the same bytes as that comparison's
  `harness/schema.json`).
- Synthetic: 4 documents generated by `synthetic/generate_p2s.py` from `synthetic/spec.json`, an extension of the
  synthetic PDF benchmark's article template (`feat/synthetic-pdf-benchmark` `1513c446`). Each prints a survey's own
  objects (40, 70, 100, 55), each with 4 to 6 sample rows and a description paragraph; cited objects of another
  museum (4, 6, 8, 5), each printed twice (a comparative section after the methods and a discussion after the own
  objects) with its catalogue and citation; and reprints of own objects (4, 6, 8, 5). Gold is exact by Object ID:
  `truth.json` per document. Schema: the benchmark's article schema, unchanged (`harness/schema-synthetic.json`).
  Parsed on Baratheon with production parsing (`harness/parse_pdf.py`, native text, no column cutting).

## Method

- Article, `context=bounded`, `context_tokens=12288`, no overlap, plain text, `record_chars` 1,000,000, as in the
  PR #267 comparison.
- Conditions N (fields `numind/NuExtract3-FP8`, reasoning `nvidia/Qwen3.8-27B-NVFP4`) and Q (both Qwen), on
  Baratheon's live vLLM servers, adapter defaults. One execution per document and condition: 32 runs. No reruns, no
  best-of-N. Failures are reported, never retried by hand. Runs go in four queues at once (N and Q, corpus and
  synthetic).
- Pairing (`harness/run_paired.py`): each run reads its parts once. The fix resolves the assembled input live and
  drives the run. The baseline (`harness/resolution_b.py`, the accepted resolver's exact bytes) then resolves the
  same assembled input; a request byte-identical to one the fix sent reuses the fix's reply, and any other request
  is sent live. Where both send the same requests, every difference is the decision rule's. Where they differ, the
  requests show why.

## Measures and acceptance

Scored by `score_p2s.py`, which runs `../pr267-resolution-comparison/score.py` unchanged for the corpus.

Corpus, per condition:

- C1. The fix passes A1-A4 exactly as the PR #267 protocol defines them.
- C2. In every run where the baseline refused no list for its budget, the baseline sent only requests the fix sent
  (all reused), and the two results differ only in copies labelled REPEAT beside an equal item labelled OTHER and none
  labelled OWN, with no scalar differing.

Synthetic, per condition, pooled over the 4 documents (an Object ID present in assembly is an own object when the
survey prints it as its own, cited when it is a cited object's):

- S1. The fix leaves no list unresolved for its length: no `resolution_exceeds_budget` in any fix run, and no fix
  call whose counted request and reply reserve exceed 12,288 tokens.
- S2. Own objects present under assembly and absent after the fix's resolution are at most 5% of the own objects
  assembly had.
- S3. No own object is absent after the fix with a copy dropped as a REPEAT beside OTHER alone (P2-1's own risk).

Reported, not criteria: how often the baseline refused a list for its budget; own, cited and unmatched copies under
assembly, the fix and the baseline; every equal group by how it was labelled; every item the fix dropped,
classified by Object ID (synthetic) or adjudicated against the source (corpus, as before); UNSURE and null list
answers; calls and failures; and the baseline's A1-A4 on the corpus.

## Decision rule

If every criterion holds in both conditions, the results go on PR #275 and the maintainer decides whether to accept
the fix. If any criterion fails, the PR stays draft and the results are posted. No fix-and-rerun cycle follows
without the maintainer. A document whose part calls all fail is excluded and reported.

## Pilots and limits declared in advance

- Three uncounted pilots ran before this protocol, all on synthetic document `p2s-a` with the fix's code, to make the
  inputs exercise the P2s. Pilot 1 (Q): a 45-page reading part's reply ran into a whitespace loop and only 5 items
  were assembled, so each object page got a description paragraph to hold about 15 objects per part. Pilot 2 (Q):
  44 items, both resolvers sent one identical request, and the reader skipped every cited object, whose text said it
  was not part of the survey. That statement was removed. Pilot 3 (N and Q): 52 items. The baseline refused the list
  for its budget and kept every cited copy; the fix resolved it in 2 parts and dropped all 8 cited copies, with no own
  object lost. In Q, 4 cited objects were labelled OTHER with their second copy REPEAT. Only the inputs changed
  between pilots; the code under test, harness, scorer and criteria did not. `p2s-a` is therefore not unseen; the
  other three documents had no model call before this protocol.
- The synthetic documents are generated to make the P2s occur and print clean, regular text. They show the rules'
  behavior where the P2s apply, not how often the P2s occur in real papers.
- The corpus run is the fourth execution on the same 12 papers. The live servers are not deterministic at
  temperature 0, and four queues share them; within a run, the fix and baseline still resolve the same readings.
- Where a list fits one 60-item part, the baseline's result is the old rule applied to the fix's reply, not an
  independent call.
