## Capability findings

### Durable signals, waits, and acknowledgement

**Finding:** Both SDKs implement database-persisted topic mailboxes: Python `send`/`recv` (and async variants), TypeScript `send`/`recv`. Receiving consumes one message and records its return value as an operation; replay returns the recorded value rather than consuming the next command. Wait deadlines are durable, so a restart does not reset a finite wait. Python defaults to a 60-second receive timeout; TypeScript supports receive options. Workflow-originated sends are checkpointed; external sends can use an idempotency key. Source: [Python recv setup/consume](https://github.com/dbos-inc/dbos-transact-py/blob/84715a3633316a3d62479516fb8d432245f5a172/dbos/_sys_db.py#L3604), [TypeScript recv](https://github.com/dbos-inc/dbos-transact-ts/blob/ba893ec9964d88b72881e9738b31d40654c8adfb/src/system_database.ts#L3252), [Python API](https://github.com/dbos-inc/dbos-transact-py/blob/84715a3633316a3d62479516fb8d432245f5a172/dbos/_dbos.py#L1650), [TypeScript API](https://github.com/dbos-inc/dbos-transact-ts/blob/ba893ec9964d88b72881e9738b31d40654c8adfb/src/dbos.ts#L1420).

**Finding:** Events (`set_event`/`get_event`, `setEvent`/`getEvent`) publish durable latest values for clients; a workflow's event read itself has replay semantics. Streams are durable append-only output, with workflow writes checkpointed and step writes potentially repeated on retry. An event is not a queue of ordered commands. Sources: [Python communication docs](https://docs.dbos.dev/python/tutorials/workflow-communication), [TypeScript communication docs](https://docs.dbos.dev/typescript/tutorials/workflow-communication).

**Inference for FREE:** These support signaling and publishing a pause acknowledgement, but receiving a request is not evidence that every underway model call has finished or that every result has been saved. A control protocol needs command identity, ordering/supersession rules, safe-point acknowledgement and durable desired state. A replayed earlier event read cannot be assumed to observe a newer setting or correction. Indefinite product pause needs explicit timeout handling rather than treating a default `recv` timeout as Resume. Sources: mailbox/event semantics above and [settled product constraints](https://github.com/HUM-CDCH/FREE/issues/169).

**Finding:** `recv` belongs in workflow control flow, not inside a step; async Python workflows must use `recv_async` and other async variants. A new receive gate cannot simply be inserted into FREE's synchronous `extract_run` step. Studio and kei also use distinct system schemas/application ownership, so cross-service commands must target the correct DBOS client/schema and remain behind Studio's authenticated owner checks. Sources: [Python receive API](https://github.com/dbos-inc/dbos-transact-py/blob/84715a3633316a3d62479516fb8d432245f5a172/dbos/_dbos.py#L1712), [TypeScript receive restriction](https://github.com/dbos-inc/dbos-transact-ts/blob/ba893ec9964d88b72881e9738b31d40654c8adfb/src/dbos.ts#L1467), [FREE client boundary](https://github.com/HUM-CDCH/FREE/blob/a1ae85b7ce500aa57ffd4025453c4703665daca7/prototypes/studio/server/dbos.ts#L26), [root ownership contract](https://github.com/HUM-CDCH/FREE/blob/a1ae85b7ce500aa57ffd4025453c4703665daca7/README.md#L29).

### Cooperative pause versus cancellation

**Finding:** Neither pinned workflow status enum contains a researcher-facing `PAUSED` status. Cancellation moves eligible runtime rows to `CANCELLED` and removes queue membership immediately; `SUCCESS` and `ERROR` are untouched. A running step is not generally forcibly stopped. TypeScript offers `DBOS.stepStatus.cancelSignal`; Python has async-step preemption options, but a native synchronous call cannot be assumed interruptible. Sources: [Python statuses and cancellation](https://github.com/dbos-inc/dbos-transact-py/blob/84715a3633316a3d62479516fb8d432245f5a172/dbos/_sys_db.py#L123), [Python cancellation update](https://github.com/dbos-inc/dbos-transact-py/blob/84715a3633316a3d62479516fb8d432245f5a172/dbos/_sys_db.py#L1162), [Python step options](https://github.com/dbos-inc/dbos-transact-py/blob/84715a3633316a3d62479516fb8d432245f5a172/dbos/_dbos.py#L1110), [TypeScript cancellation and resume](https://github.com/dbos-inc/dbos-transact-ts/blob/ba893ec9964d88b72881e9738b31d40654c8adfb/src/system_database.ts#L1936), [TypeScript step cancellation watcher](https://github.com/dbos-inc/dbos-transact-ts/blob/ba893ec9964d88b72881e9738b31d40654c8adfb/src/dbos-executor.ts#L943).

**Inference for FREE:** Runtime cancellation is not the settled product Pause contract: the requested acknowledgement waits for safe underway units and persistence, while the runtime status changes first. Passing TypeScript's cancel signal to `fetch` intentionally aborts a request, which also differs from finishing a safe model unit. A durable receive-based gate can remain paused after replay if the application records/control-replays that gate, but DBOS does not provide the entire lifecycle protocol. Sources: [TypeScript management docs](https://docs.dbos.dev/typescript/tutorials/workflow-management), pinned cancellation code above, [#169](https://github.com/HUM-CDCH/FREE/issues/169).

### Restart, completed steps, interrupted work, and retries

**Finding:** Recovery reexecutes workflow control flow using saved inputs; completed operations return their saved result. An interrupted step without a persisted outcome can run again in full. An ordinary final step error is persisted and rethrown on replay; automatic retry is bounded within that step's execution and controlled by its predicate. Python specifically does not record a step outcome for `DBOSWorkflowCancelledError`. TypeScript checks cancellation around attempt failures before recording an ordinary error. Sources: [Python step execution](https://github.com/dbos-inc/dbos-transact-py/blob/84715a3633316a3d62479516fb8d432245f5a172/dbos/_core.py#L2240), [TypeScript step execution](https://github.com/dbos-inc/dbos-transact-ts/blob/ba893ec9964d88b72881e9738b31d40654c8adfb/src/dbos-executor.ts#L926).

**Finding:** Python startup recovery considers pending workflows for the executor/version and re-enqueues through an atomic queue handoff. Resume in **both** SDKs excludes `SUCCESS` and `ERROR`; it resets recovery attempts/deadline and enqueues other eligible states onto a named queue, or the internal queue when omitted. It does not accept replacement inputs, erase a saved step error, or retry a successfully returned failure envelope. Sources: [Python recovery](https://github.com/dbos-inc/dbos-transact-py/blob/84715a3633316a3d62479516fb8d432245f5a172/dbos/_recovery.py#L13), [Python resume](https://github.com/dbos-inc/dbos-transact-py/blob/84715a3633316a3d62479516fb8d432245f5a172/dbos/_sys_db.py#L1206), [TypeScript resume](https://github.com/dbos-inc/dbos-transact-ts/blob/ba893ec9964d88b72881e9738b31d40654c8adfb/src/system_database.ts#L1953).

**Inference for FREE:** A researcher retry after failure cannot be implemented by calling Resume indiscriminately. Even a resumable cancelled history may contain an ordinary recorded step error; that boundary must be inspected. Saved external progress can prevent repeating accepted work when the containing step reruns, but that is an application guarantee, not automatic DBOS per-model-call durability. Sources: step replay and resume code above.

### Queue slots and concurrency

**Finding:** In both locked SDKs worker concurrency is counted from active executions in memory; global concurrency uses live pending database rows. Durable `recv`/sleep waits remain executions and do not automatically release workflow concurrency slots. Cancellation removes queue membership/status before a native step necessarily returns; its local active execution can still consume a worker slot. Sources: [Python queue runner](https://github.com/dbos-inc/dbos-transact-py/blob/84715a3633316a3d62479516fb8d432245f5a172/dbos/_queue.py#L690), [Python dequeue limits](https://github.com/dbos-inc/dbos-transact-py/blob/84715a3633316a3d62479516fb8d432245f5a172/dbos/_sys_db.py#L4684), [TypeScript running registry](https://github.com/dbos-inc/dbos-transact-ts/blob/ba893ec9964d88b72881e9738b31d40654c8adfb/src/system_database.ts#L2859), [TypeScript dequeue limits](https://github.com/dbos-inc/dbos-transact-ts/blob/ba893ec9964d88b72881e9738b31d40654c8adfb/src/system_database.ts#L3920).

**Finding:** FREE's `kei-extract` lane has global concurrency **2** and worker concurrency **2**; `KEI_CATALOG_CHUNKS` controls additional model-call threads inside each extraction. Studio's `studio` queue is unrestricted. Thus workflow slots and model capacity are different limits. Sources: [kei queue configuration](https://github.com/HUM-CDCH/FREE/blob/a1ae85b7ce500aa57ffd4025453c4703665daca7/prototypes/parsing_service/src/kei_exp/workflows/config.py#L17), [chunk configuration](https://github.com/HUM-CDCH/FREE/blob/a1ae85b7ce500aa57ffd4025453c4703665daca7/prototypes/parsing_service/src/kei_exp/workflows/extract.py#L33), [Studio queues](https://github.com/HUM-CDCH/FREE/blob/a1ae85b7ce500aa57ffd4025453c4703665daca7/prototypes/studio/server/dbos.ts#L123).

**Inference for FREE:** Parking two paused extractions in a receive on the constrained Python lane can occupy all of it. Resuming without naming that lane routes through the internal queue and bypasses its configured capacity boundary. Neither outcome is a neutral implementation choice; checkpoint/lifecycle design must specify how paused work releases capacity and how resumed work re-enters admission. Cancellation alone does not prove physical quiescence across workers. Sources: pinned queue and resume implementations above.

### Workflow identity, changing inputs, and idempotency

**Finding:** Runtime identity is an idempotency boundary for starting a workflow, not an input revision. Reusing an existing ID is not a general input-edit operation. Recovery uses saved input and operation history. Both SDKs offer **fork**: a new workflow ID, original input, and copied pre-cut operations, with optional application version/queue controls but no general replacement-input argument. **Rewind** also exists in both locked versions: same ID, discarded post-cut history, terminal-state precondition. Python's first operation cut is 1; TypeScript defaults to 0. Rewind also changes events/mailbox history and leaves stream history with special close handling, so it is not an audit-preserving resume. Sources: [Python fork/rewind API](https://github.com/dbos-inc/dbos-transact-py/blob/84715a3633316a3d62479516fb8d432245f5a172/dbos/_dbos.py#L2399), [Python fork copy](https://github.com/dbos-inc/dbos-transact-py/blob/84715a3633316a3d62479516fb8d432245f5a172/dbos/_sys_db.py#L1650), [Python rewind](https://github.com/dbos-inc/dbos-transact-py/blob/84715a3633316a3d62479516fb8d432245f5a172/dbos/_sys_db.py#L1457), [TypeScript API](https://github.com/dbos-inc/dbos-transact-ts/blob/ba893ec9964d88b72881e9738b31d40654c8adfb/src/dbos.ts#L1106), [TypeScript fork copy](https://github.com/dbos-inc/dbos-transact-ts/blob/ba893ec9964d88b72881e9738b31d40654c8adfb/src/system_database.ts#L2403).

**Finding:** A narrow exception exists for debounced, still-`DELAYED` workflows: both SDKs can update their inputs before execution. This is not a supported way to edit an already-running extraction's history. Sources: [Python delayed debounce update](https://github.com/dbos-inc/dbos-transact-py/blob/84715a3633316a3d62479516fb8d432245f5a172/dbos/_sys_db.py#L1310), [TypeScript delayed debounce update](https://github.com/dbos-inc/dbos-transact-ts/blob/ba893ec9964d88b72881e9738b31d40654c8adfb/src/system_database.ts#L1989).

**Inference for FREE:** Keeping the same researcher-visible Extraction does not require keeping one runtime ID. Fresh execution segments with explicit revision IDs, or control messages/durable state read at new safe boundaries, are possible capability-level approaches; this research chooses neither. Fork alone does not apply new settings if the retained input/checkpoints already pin old ones. Rewind conflicts with the ticket's no-history-rewrite constraint. An external model request or filesystem/database publication may run again after the process dies before the DBOS outcome write; idempotency needs stable application keys, validated write-once/reuse records, conditional result acceptance, or an atomic supported transaction boundary. DBOS history does not make an arbitrary remote call exactly once. Sources: fork/input and step execution code above.

## FREE integration constraints

**Finding:** Studio derives runtime IDs `extract:<Extraction ID>` and `kei-extract:<Extraction ID>`; Python derives the artifact extraction ID from its workflow ID, and Studio validates that returned ID against the Extraction. New runtime IDs therefore require an explicit mapping/contract rather than adding an arbitrary suffix. Workflow input carries IDs in Studio, but `loadAdmitted` checkpoints the full admitted pins/settings/schema; the Python portable child request includes that snapshot. Sources: [identity and handoff](https://github.com/HUM-CDCH/FREE/blob/a1ae85b7ce500aa57ffd4025453c4703665daca7/packages/extraction/src/kei-handoff.ts#L53), [Python ID derivation](https://github.com/HUM-CDCH/FREE/blob/a1ae85b7ce500aa57ffd4025453c4703665daca7/prototypes/parsing_service/src/kei_exp/workflows/contracts.py#L121), [Studio workflow](https://github.com/HUM-CDCH/FREE/blob/a1ae85b7ce500aa57ffd4025453c4703665daca7/packages/extraction/src/workflows.ts#L146).

**Finding:** Python's extraction workflow currently has one `extract_run` step covering extraction and final artifact publication. Its automatic policy retries transient backend failures three times (5/10-second waits). `settled` converts ordinary failure/retry exhaustion into an `ok:false` return: the DBOS workflow can be `SUCCESS` while the Extraction fails. Studio publishes a terminal failure/result and its workflow returns normally too. Sources: [extraction step](https://github.com/HUM-CDCH/FREE/blob/a1ae85b7ce500aa57ffd4025453c4703665daca7/prototypes/parsing_service/src/kei_exp/workflows/extract.py#L62), [retry policy](https://github.com/HUM-CDCH/FREE/blob/a1ae85b7ce500aa57ffd4025453c4703665daca7/prototypes/parsing_service/src/kei_exp/failures.py#L86), [failure envelope](https://github.com/HUM-CDCH/FREE/blob/a1ae85b7ce500aa57ffd4025453c4703665daca7/prototypes/parsing_service/src/kei_exp/workflows/contracts.py#L101), [Studio settlement](https://github.com/HUM-CDCH/FREE/blob/a1ae85b7ce500aa57ffd4025453c4703665daca7/packages/extraction/src/workflows.ts#L170).

**Finding:** Unified Catalog already reuses validated write-once execution/discovery/finished-entry records on a retry of that single step. Reading markers and candidate stage files are progress-only and explicitly excluded from recovery reuse. Other method boundaries cannot be assumed to have the same reuse guarantees. FREE's cancel check finishes the model call then checks status; it raises an ordinary `KeiFailure('cancelled', ...)`, not Python's special DBOS cancellation exception. Consequently, do not assume Resume alone will re-run a cancelled step cleanly: ordinary error checkpoint replay matters. Sources: [Unified Catalog reuse](https://github.com/HUM-CDCH/FREE/blob/a1ae85b7ce500aa57ffd4025453c4703665daca7/prototypes/parsing_service/src/kei_exp/kie/extract/unified.py#L301), [cancel check](https://github.com/HUM-CDCH/FREE/blob/a1ae85b7ce500aa57ffd4025453c4703665daca7/prototypes/parsing_service/src/kei_exp/workflows/cancel.py), [Python ordinary error checkpoint](https://github.com/dbos-inc/dbos-transact-py/blob/84715a3633316a3d62479516fb8d432245f5a172/dbos/_core.py#L2274).

**Inference:** The accepted future behavior needs a validated partial-result authority, provenance per saved result, preservation of manual corrections, explicit unfinished-work selection, and a lifecycle acknowledgement boundary. The existing progress files cannot acquire those guarantees merely by being made visible after Stop/failure. Editing schema/settings requires new revision-aware execution semantics because current admission pins are immutable; this changes the existing contract and must be specified explicitly. Sources: [root contract](https://github.com/HUM-CDCH/FREE/blob/a1ae85b7ce500aa57ffd4025453c4703665daca7/README.md#L29), [domain context](https://github.com/HUM-CDCH/FREE/blob/a1ae85b7ce500aa57ffd4025453c4703665daca7/CONTEXT.md), [Parsing Service contract](https://github.com/HUM-CDCH/FREE/blob/a1ae85b7ce500aa57ffd4025453c4703665daca7/prototypes/parsing_service/README.md), [#169](https://github.com/HUM-CDCH/FREE/issues/169).

## Compatibility and deployment findings

**Finding:** Both locked SDKs expose patch/deprecate-patch primitives that preserve operation numbering and branch selection using history markers. Patching requires enabling the feature and calling it in workflow control flow, not inside the giant extraction step. It does not edit input, invalidate a saved output, or teach the runtime about changed internal model-call boundaries. Sources: [Python patch](https://github.com/dbos-inc/dbos-transact-py/blob/84715a3633316a3d62479516fb8d432245f5a172/dbos/_dbos.py#L3649), [Python marker storage](https://github.com/dbos-inc/dbos-transact-py/blob/84715a3633316a3d62479516fb8d432245f5a172/dbos/_sys_db.py#L6088), [TypeScript patch](https://github.com/dbos-inc/dbos-transact-ts/blob/ba893ec9964d88b72881e9738b31d40654c8adfb/src/dbos.ts#L2143).

**Finding:** FREE enables patching and fixes versions at `kei@1` and `studio@1`; local contracts require changed step sequences behind `DBOS.patch()` and a drain before changing these versions. Official upgrade guidance supports maintaining compatible history through patching or routing old executions to their application version. Removal follows patch deprecation after affected histories can no longer reexecute. Sources: [Python version contract](https://github.com/HUM-CDCH/FREE/blob/a1ae85b7ce500aa57ffd4025453c4703665daca7/prototypes/parsing_service/CLAUDE.md), [Studio version contract](https://github.com/HUM-CDCH/FREE/blob/a1ae85b7ce500aa57ffd4025453c4703665daca7/prototypes/studio/CLAUDE.md), [Python upgrade docs](https://docs.dbos.dev/python/tutorials/upgrading-workflows), [TypeScript upgrade docs](https://docs.dbos.dev/typescript/tutorials/upgrading-workflows).

**Inference:** Long-lived paused histories make “drained” a concrete policy question: paused/cancelled executions intended to resume still need compatible code, even if no model call is active. A future specification must define treatment of such retained histories before a version bump/removing old branches; changing code inside a step also needs an application record-format/reuse compatibility rule. No deployment/version change is proposed here.

## Questions retained for the map

These are constraints for the existing lifecycle/checkpoint/schema decisions, not newly opened issues: which owner durably acknowledges quiescence and releases constrained capacity; which safe units and accepted partial artifacts each method supports; how execution revision/runtime identity maps to one Extraction without overwriting corrections; how revised inputs are consumed only by future work; and how paused histories enter the drain/version policy. Source: capability findings above and [parent map](https://github.com/HUM-CDCH/FREE/issues/169).
